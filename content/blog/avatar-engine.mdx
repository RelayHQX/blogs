When you open an email app like Relay, you expect it to feel effortless. As you flick-scroll through your inbox, profile pictures and company logos should appear instantly next to each conversation. If someone doesn't have a picture, the app seamlessly shows their colorful initials.

It sounds deceptively simple: it's just a tiny picture next to an email address.

Behind the scenes, however, avatar resolution is one of the most demanding tasks in app development. An active inbox contains hundreds of emails, rapid scrolling, and continuous background syncing. Every single time a new message appears on screen, your phone has barely **16 milliseconds** to figure out who sent it, look up their image, and draw it on display before the animation drops a frame.

If the avatar engine stutters, leaks memory, or hammers the internet with redundant requests, your entire app feels sluggish, your phone heats up, and your battery drains.

We recently replaced Relay's legacy in-repo avatar engine (`src/services/avatarEngine.ts`) with a ground-up external open-source package: **`@rhq/avatar`**. 

The results transformed the experience: **15 million reads per second**, zero memory leaks, **98.6% less cellular data used**, and a **3,080x speedup** when scrolling past contacts.

Here is the story of why our original engine broke down, how we re-engineered it, and how these optimizations make Relay feel lightning fast.

## The 5 Hidden Bottlenecks of Our Legacy Engine

When we audited Relay's previous avatar engine under real-world conditions (simulating a busy inbox with 3,000+ incoming contacts), five major architectural flaws emerged:

### 1. Checking the Clock 100,000 Times a Second
To check if a cached avatar had expired, the old engine asked the phone's operating system for the exact hardware timestamp (`Date.now()`) on every single lookup. 

> **Everyday Analogy**: Imagine reading a book, but after every single word, you stop, walk across the room to check a wall clock, and write down the exact millisecond. You would never finish reading. When scrolling through a contact list, thousands of clock checks created needless CPU friction and drained battery power.

### 2. The Hoarding Problem (Unbounded Memory Leaks)
The old engine kept every cached avatar in a plain JavaScript list with no maximum capacity and no cleanup schedule. 

> **Everyday Analogy**: Imagine never taking out the trash. Every piece of junk mail you receive gets stacked in your living room forever. For users who receive emails from thousands of newsletters, automated bots, and clients, the app's memory footprint grew endlessly until the mobile operating system killed the app to prevent a system crash.

### 3. The Repeated Door-Knocking Bug (Negative Caching)
This was the single most destructive bug in our old engine. When an email sender had no profile picture (like `notifications@service.com`), the engine correctly fell back to initials and saved:

```ts
avatarCache.set(key, { url: null, source: 'initials' });
```

However, the lookup helper contained this tiny oversight:

```ts
function getCachedAvatar(key: string) {
  const cached = avatarCache.get(key);
  if (cached && cached.url) return cached;
  return null; // Bug: null url was treated as a complete cache miss!
}
```

Because `cached.url` was `null`, the function returned `null`! The app concluded: *"We have never checked this person before!"*

Every time you scrolled past that contact, Relay knocked on three external servers (Gravatar, Unavatar, Libravatar) asking if they had an image yet. Scrolling past 10 avatarless emails triggered **30 wasted internet requests** on every single scroll gesture, turning smooth 120Hz scrolling into noticeable stutter.

### 4. Downloading the Entire Book Just to Read the Title
To verify whether a contact had a Gravatar or company logo on the internet, the old engine downloaded the full image file (~18.5 KB) into memory.

> **Everyday Analogy**: Imagine you want to check if a store is open. Instead of glancing through the window, you walk inside, purchase every item on the shelf, carry them home, and throw them away. You only needed to know if the store was open! Downloading full images repeatedly wasted cellular megabytes and forced the phone's memory cleaner to work overtime.

### 5. Desktop-Only Cryptography on Mobile Devices
To turn an email address into a secure Gravatar hash (like `contact@example.com` into a SHA-256 fingerprint), the legacy engine relied on desktop Node.js C++ bindings. Making this work on mobile phones required heavy polyfills and slowed down startup times.

## How `@rhq/avatar` Solves These Problems

We engineered `@rhq/avatar` from scratch as an independent, lightweight, universal package designed to solve each bottleneck at the micro-architectural level:

1. **Dual-TTL Memory Caching**: Real profile photos stay cached for 24 hours. Contacts with no photo are remembered as "negative" for 1 hour. Scrolling past avatarless contacts now resolves in **0.10 milliseconds with zero internet traffic**.
2. **Coarse-Time Sampling**: Instead of interrogating the operating system clock 100,000 times a second, `@rhq/avatar` samples the time once per frame tick. Synchronous lookup throughput skyrocketed to **15,000,000 lookups per second**.
3. **Range 0-0 Probing**: To check if an avatar exists on the web, `@rhq/avatar` asks the server for only the very first byte (`Range: bytes=0-0`). As soon as the server answers HTTP 206, the engine immediately cancels the connection. Bandwidth plummeted from **18.5 KB down to 256 bytes—a 98.6% reduction**.
4. **Strict 1,000-Item LRU Limit**: When memory reaches 1,000 items, the oldest untouched contacts are quietly cleaned up. Memory stays strictly bounded, guaranteeing zero crashes.
5. **Universal Pure-JS & WebCrypto Pipeline**: Email hashing runs natively in any environment—Web, React Native, Node.js, and Hermes—at over 1.1 million hashes per second.

## The 3-Tier Storage Hierarchy

Think of avatar caching like an efficient office desk:

- **Tier 1: In-Memory LRU (L1)**: Like papers currently in your hand. Resolves in 66 nanoseconds with zero battery cost.
- **Tier 2: Persistent Storage (L2)**: Like files in your desk drawer. Saved on your device so that when you reboot your phone or open the app cold, your top 1,000 contacts restore in 2.68 milliseconds without touching the internet.
- **Tier 3: Range Prober (Network)**: Like calling the warehouse. Only used for contacts you have never seen before, transferring just 256 bytes.

| **Startup Network Penalty** | Fresh network fetches triggered | **Zero network requests** | Instant initial screen render |

## Architectural Comparison Matrix

| Feature | Legacy In-Repo Engine | `@rhq/avatar` Package |
| :--- | :--- | :--- |
| **Distribution** | Monolithic code inside app repo | Standalone NPM module (`@rhq/avatar`) |
| **L1 Memory Cache** | Unbounded `Map` (memory leak) | Bounded Dual-TTL LRU Cache (`AvatarCache`) |
| **L2 Persistence Adapter** | Hardcoded React Native AsyncStorage | Pluggable adapter (AsyncStorage, localStorage, Redis) |
| **Negative Result Caching** | Broken (treated as miss, loop queries) | Supported (`negativeTtl` defaults to 3,600s) |
| **Network Probing** | Full GET payload download (~18.5 KB) | `Range: bytes=0-0` + `body.cancel()` (~256 B) |
| **Resolution Policies** | Hardcoded waterfall only | Pluggable (`'first-match'`, `'fastest'`, `'verified-only'`) |
| **SHA-256 Engine** | Node.js `crypto` only | Universal memoized pipeline (Web Crypto + pure JS) |
| **Framework Compatibility** | React Native only | React, React Native, Expo, Node.js, Next.js, Vanilla JS |
